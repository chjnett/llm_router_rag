CapRoute는 “작은 LLM과 큰 LLM 중 무엇을 쓸까?”보다 앞단의 문제를 다룹니다. 과학 논문 PDF를 텍스트로 빠르게 처리할지, 그림과 표까지 이해하는 강한 처리기를 호출할지를 질문별로 선택합니다.

대상: 영문 born-digital 과학 논문 PDFGPU: RTX 3090 24GB현재 단계: 외부 비용 Gate 실패 · Router 재설계
한 문장으로먼저 저렴한 텍스트 검색으로 답을 찾고, 그 결과가 부족할 가능성이 높은 질문만 시각 검색기로 다시 확인한다.

목표는 최고 모델보다 더 높은 정답률을 약속하는 것이 아니라, 적은 Strong 호출로 텍스트 기준선의 품질을 지키거나 개선하는 것입니다.

01 · Why

도서관 사서로 비유하면 쉽다

논문 한 편에는 본문, 수식, 표, 그래프가 섞여 있습니다. 모든 질문에 가장 비싼 분석을 적용하면 정확할 수 있지만 느리고 저장 공간도 커집니다.

CHEAP목차와 캡션부터 찾기

텍스트 임베딩으로 빠르게 관련 표·그림 후보를 찾습니다. 싸고 빠르지만 이미지 내부 정보는 충분히 보지 못합니다.

STRONG실제 페이지를 자세히 보기

ColSmol 같은 시각 모델이 이미지 내용을 다중 벡터로 읽습니다. 더 풍부하지만 GPU 시간과 인덱스 비용이 듭니다.

ROUTER누구에게 맡길지 결정하기

Cheap 결과의 점수·간격·불확실성과 질문 표현을 보고 Strong 경로가 도움이 될 가능성을 예측합니다.

02 · Current architecture

현재 후보 아키텍처의 전체 흐름

초기에는 PDF를 저장할 때 페이지별 parser를 선택하려 했습니다. Oracle 절감 상한이 9.86%에 그쳐 실패했고, 지금은 실제 질문이 들어온 뒤 필요한 페이지만 구제하는 구조로 피봇했습니다.

Cheap 문서 인덱스

PDF 텍스트·캡션을 추출하고 BGE 임베딩을 저장합니다. 모든 질문이 이용하는 기본 경로입니다.

5 · DOWNSTREAM

근거 기반 답변

선택한 표·그림과 provenance를 답변 모델에 전달합니다. 현재 연구는 검색 단계 검증에 집중합니다.

중요: ColSmol은 PDF parser나 답변 LLM이 아니라, 질문과 페이지 이미지를 비교하는 visual retriever입니다.

인과 구조는 수리했지만 비용 일반화는 실패

Early router는 실제로 Strong 계산을 건너뛸 수 있고 외부 품질도 개선했습니다. 다만 SciVQA test에서 Strong skip이 10.35%에 그쳐 사전 목표 15%를 통과하지 못했습니다.

03 · Components

각 부품이 실제로 하는 일

아키텍처 문서의 용어를 구현 단위로 풀어쓴 설명입니다.

1

Native PDF scan

PyMuPDF로 텍스트 레이어, 페이지 수, 이미지·표 단서를 빠르게 읽습니다. 스캔 PDF가 아닌 born-digital PDF로 범위를 제한합니다.

2

Caption text representation

표·그림 캡션을 BGE-small 임베딩으로 바꾸고 질문과의 의미 유사도를 계산합니다. 현재 Cheap 기준선입니다.

3

Visual representation

ColSmol-256M이 이미지와 질문을 여러 토큰 벡터로 표현하고 MaxSim으로 순위를 만듭니다.

4

Capability router

“질문이 어려운가?”가 아니라 “이 질문에서 visual 결과가 caption보다 나을 것인가?”를 Logistic Regression으로 예측합니다.

5

Early policy threshold

Cheap-only 확률이 0.328183 이상일 때만 ColSmol을 실행합니다. SPIQA calibration 94문항에서 정하고 SciVQA test를 열기 전에 잠갔습니다.

6

Canonical result & provenance

어느 문서·질문·경로·모델에서 결과가 나왔는지 기록합니다. 동일한 결과를 재사용하도록 inference output을 cache합니다.

04 · Router logic

라우터는 확률을 어떻게 판단하는가

정답이나 Strong 결과를 입력으로 사용하지 않습니다. Strong 실행 전에 얻을 수 있는 7개 특징만 사용합니다.

p(visual이 도움됨) = sigmoid(w · standardized_features + b)

질문 특징

질문 길이, table·figure·graph·chart 같은 표현 포함 여부

Cheap 검색 신뢰도

Caption의 1등 점수, 1·2등 점수 차이, 점수 분포 entropy

문서 후보 특징

후보 이미지 개수의 로그. ColSmol 파생 점수나 두 검색기의 차이는 사용하지 않습니다.

if p ≥ 0.328183 → ColSmol 실행 후 그 순위 사용
else → ColSmol 생략, Caption BGE 순위 사용
이제 호출 절감률을 직접 셀 수 있다

p 계산에 ColSmol 값이 전혀 필요하지 않습니다. 따라서 Caption 경로를 고르면 Strong query encoding과 MaxSim을 실제로 생략합니다. 기존 13-feature 모델은 비용 라우터가 아니라 선택적 late fuser로만 남깁니다.

왜 margin을 보는가?

1등과 2등 점수가 거의 같으면 검색기가 확신하지 못하는 상황일 수 있습니다. 단, margin 하나만으로 결정하지 않고 여러 신호를 함께 봅니다.

왜 threshold를 잠그는가?

인증 결과를 본 뒤 기준을 바꾸면 시험 문제에 답을 맞추는 것과 같습니다. Calibration에서 한 번 정하고 certification 결과가 나빠도 수정하지 않습니다.

05 · Evaluation design

데이터를 왜 세 부분으로 나누는가

같은 논문의 비슷한 그림이 여러 split에 들어가면 성능이 부풀 수 있습니다. 따라서 질문이 아니라 논문 ID 기준으로 완전히 분리합니다.

TRAIN 28650 papers · 모델 계수 학습
CAL 9416 papers · threshold 선택
CERT 8113 papers · 마지막 1회 평가
앞선 표본도 분리

초기 preflight 50문항·confirmation 100문항의 39개 논문은 확대 실험에서 모두 제외했습니다.

Certification 이후 금지

SPIQA test-A의 118개 논문을 모두 사용했으므로 같은 데이터에서 특징·모델·임계값을 다시 조정하지 않습니다.

07 · Honest failure map

실패가 현재 구조를 어떻게 만들었는가

이 프로젝트는 결과에 맞춰 기준을 낮추지 않고, 각 Gate 실패가 다음 피봇의 근거가 되도록 기록합니다.

INGESTION ROUTING · FAIL

PyMuPDF vs Docling Oracle 절감 9.86%

완벽한 라우터를 가정해도 목표 15%를 못 넘어서 페이지 저장 단계 라우팅을 주력에서 내렸습니다.

QASPER RETRIEVAL · FAIL / CONDITIONAL

문단 R@5 Gate 실패, page rescue는 cache 조건부 절감

인접 페이지 rescue는 recall 97.06%와 Strong 시간 18.26% 절감을 보였지만 shared cache가 없으면 더 비쌌습니다.

VISUAL PREFLIGHT · MIXED

Visual 단독은 약하지만 Oracle 보완성 발견

“Always Visual” 대신 “어떤 질문에서 Visual이 도움되는가?”로 연구 질문을 좁혔습니다.

INITIAL SELECTOR · FAIL

50문항 학습은 100문항에서 R@1 65→62%

소표본 과적합을 확인하고 논문 단위 train/calibration/certification을 확대했습니다.

EXPANDED SELECTOR · CONDITIONAL

R@1 67.9→71.6%, 통계는 미확정

다음 단계는 같은 SPIQA 반복이 아니라 외부 데이터에서 고정 정책을 검증하는 것입니다.

INPUT RESOLUTION · PASS

ColSmol R@1 36→58%, MRR .573→.721

같은 256M 모델에서 224px 대신 원본 이미지를 사용하자 표 R@1이 52→80%로 상승했습니다. 모델 크기 전에 전처리 손실을 확인해야 한다는 근거입니다.

500M MODEL · STOP

R@1은 58%로 동일, MRR은 +0.002

그림은 조금 좋아졌지만 표는 하락했고 저장공간은 약 2배가 됐습니다. 현재는 256M+원본 해상도가 더 효율적입니다.

SCIVQA VALIDATION · MIXED

품질 +4.86%p, 실제 compute saving 0%

통계적 품질 개선은 재현됐지만 Strong 점수 특징 때문에 계산을 건너뛸 수 없었습니다. Early router와 late fuser를 분리했습니다.

SCIVQA TEST · COST FAIL

품질 +2.98%p, Strong skip 10.35%

인과적 early router의 품질은 재현됐지만 15% 절감 Gate에 실패했습니다. Candidate 규모 1–29→599의 분포 이동이 주요 원인입니다.

08 · What happens next

다음 단계와 통과 조건

GPU를 오래 돌리는 것 자체가 목표가 아닙니다. 새로운 독립 증거가 생기는 실험만 실행합니다.

1. Cheap-only early router · 완료

질문·후보 수·Caption score/margin/entropy만 보는 7-feature 정책을 구현했습니다.

2. Policy lock · 완료

SPIQA train/calibration에서 threshold 0.328183을 잠갔습니다. 내부 Strong skip은 61.70%입니다.

3. SciVQA test one-shot · FAIL

품질 retention은 100%를 넘었지만 실제 Strong skip 10.35%로 비용 기준 15%를 통과하지 못했습니다.

4. 다음 허용 작업

같은 test는 잠급니다. 새 development corpus에서 corpus-size invariant 특징과 cost-sensitive objective를 만들고 새로운 holdout에서만 다시 인증합니다.
